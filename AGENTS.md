### Hosting / despliegue
- La app corre con un servidor custom (`server.ts`, para poder usar Socket.io) — no es compatible con hosting serverless "puro" (tipo Vercel) para la parte de websockets; necesita un proceso Node persistente (VPS, Droplet, Railway, Fly.io, Render, etc., con o sin Docker).

Redis) porque las conexiones WebSocket quedan atadas a una instancia — revisar esto antes de escalar horizontalmente, no hace falta para una sola instancia.

### Seguridad (revisar antes de producción)
- **SQL injection: no es un problema hoy.** Todo el acceso a datos pasa por Prisma (query builder parametrizado) — no hay un solo `$queryRaw`/`$executeRaw`/`queryRawUnsafe` en `src/` (grep completo, cero resultados), ni construcción de SQL a mano en ningún lado. Mientras se siga sin usar `$queryRaw` con interpolación de strings, no hay vector de SQL injection clásico. Si en algún momento se necesita una query cruda (para algo que Prisma no exprese bien), usar SIEMPRE `$queryRaw` con template tag (parametrizado) y nunca `$queryRawUnsafe`/concatenación de strings.
- ~~**CRÍTICO** — `POST /api/suscripcion` permitía autoconcederse un plan pago gratis, para siempre~~ — **arreglado 2026-09-07**: la ruta aceptaba `plan: "PROFESIONAL"|"PREMIUM"` y los activaba (`estado:"ACTIVA"`) sin verificar ningún pago real de MercadoPago — cualquier profesional con perfil `APROBADO` podía hacer `POST /api/suscripcion {"plan":"PREMIUM"}` y quedar con Premium activo sin pagar. Peor: al crear/actualizar la suscripción para un plan pago, `fechaFin` quedaba `undefined` (nunca seteado) → permanecía `null` → nunca vencía, ni siquiera lo agarraba el scheduler de `verificar-vencidas` (que solo mira suscripciones con `fechaFin` vencida). El frontend (`src/app/planes/page.tsx`) nunca llamó a esta ruta con un plan pago (los pagos siempre van por `/api/suscripcion/checkout` → MercadoPago → webhook), así que no había ningún uso legítimo que se perdiera al cerrarlo: ahora la ruta rechaza cualquier `plan` que no sea `"GRATUITO"` con un 400 explícito. **Pendiente**: valdría la pena revisar si en algún momento de las pruebas de esta sesión o anteriores quedó alguna suscripción `ACTIVA` con `fechaFin: null` y sin `mercadopagoPreapprovalId`/pago real detrás (autoconcedida por este bug) — si aparece alguna, corregirla a mano.
- ~~**Cobertura de validación de inputs pareja**: 9 de 44 rutas de `/api` usan Zod~~ — auditoría dirigida (no exhaustiva de las 44) esta sesión encontró y arregló un caso real, no solo teórico:
  - **`PUT /api/profesionales/[id]`** no validaba nada del body (a diferencia de `POST /api/profesionales`, que sí usa Zod para los mismos campos).

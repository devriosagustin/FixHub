- ~~Hoy solo se usa `prisma db push` (`db:push` en `package.json`), no hay carpeta `prisma/migrations`~~ — **arreglado 2026-09-07**: se agregaron los scripts `db:migrate` (`prisma migrate dev`) y `db:migrate:deploy` (`prisma migrate deploy`) a `package.json`, y se generó el baseline (`prisma/migrations/0_init/migration.sql`, a partir del esquema actual, marcado como ya aplicado con `prisma migrate resolve --applied 0_init` sin volver a ejecutar el SQL, porque la base ya tenía ese estado por `db push`). **Ojo con el mismo problema si se regenera algo similar en PowerShell**: `npx prisma migrate diff ... > archivo.sql` con la redirección `>` de PowerShell 5.1 escribe el archivo en UTF-16LE (no UTF-8) — Prisma espera UTF-8 al leer migraciones, así que un `migration.sql` así puede fallar o comportarse mal si se re-ejecuta (ej. `prisma migrate deploy` contra una base nueva). De acá en más, usar `db:migrate` (dev) / `db:migrate:deploy` (prod/CI) en vez de `db:push` para cambios de esquema, que además puede aplicar cambios destructivos sin avisar en modo no interactivo.

### Hosting / despliegue
- La app corre con un servidor custom (`server.ts`, para poder usar Socket.io) — no es compatible con hosting serverless "puro" (tipo Vercel) para la parte de websockets; necesita un proceso Node persistente (VPS, Droplet, Railway, Fly.io, Render, etc., con o sin Docker).
- Si en algún momento se corre más de una réplica/instancia para escalar, Socket.io necesita sticky sessions en el balanceador de carga (o un adapter compartido, ej. Redis) porque las conexiones WebSocket quedan atadas a una instancia — revisar esto antes de escalar horizontalmente, no hace falta para una sola instancia.
- `docker-compose.yml` expone la app en HTTP plano (puerto 3000) — hace falta un reverse proxy delante (Caddy, Nginx, Traefik, o el proxy del proveedor de hosting) que termine TLS con el dominio real; MercadoPago (`back_url`, webhooks) y NextAuth necesitan HTTPS.
- Logging: hoy todo va a stdout del contenedor (`dev-server.log` es solo la costumbre de desarrollo local, redirigiendo la salida a un archivo) — definir dónde se van a revisar los logs en producción y si conviene algo tipo Sentry para enterarse de errores sin tener que ir a mirar logs a mano.
- Nunca commitear un `.env` real ni bakear credenciales en la imagen Docker — usar el mecanismo de secretos/variables de entorno del hosting que se elija.
